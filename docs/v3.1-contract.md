# Change Request Contract: Wordfence Firewall Summary-Compatible Metrics

**Project:** Simula Security Telemetry for Wordfence  
**Repository:** `simula-lab/simula-security-telemetry-for-wordfence`  
**Document type:** Engineering change request / implementation contract  
**Priority:** High  
**Status:** Proposed  
**Prepared:** 2026-08-05

---

## 1. Diagnosis

### 1.1 Observed discrepancy

For the site `syrianfeministlobby.org`, the Wordfence Firewall Summary reported:

| Period | Complex | Brute Force |                        Blocklist | Total |
| ------ | ------: | ----------: | -------------------------------: | ----: |
| Today  |      52 |         451 | unavailable/free-license display |   503 |
| Week   |     121 |       1,221 | unavailable/free-license display | 1,342 |
| Month  |     627 |       5,227 | unavailable/free-license display | 5,854 |

The Simula plugin exported:

```promql
wordpress_wordfence_blocked_events_total{site="syrianfeministlobby.org"} 3651
```

and:

```promql
wordpress_wordfence_blocked_events_window{
  site="syrianfeministlobby.org",
  window="24h"
} 88
```

```promql
wordpress_wordfence_blocked_events_window{
  site="syrianfeministlobby.org",
  window="7d"
} 395
```

The 24-hour plugin value is approximately 17.5% of the Wordfence “Today” total, and the 7-day plugin value is approximately 29.4% of the Wordfence “Week” total.

### 1.2 Root cause

The discrepancy is primarily semantic and data-source related, rather than evidence of a Prometheus rendering or arithmetic failure.

The existing Simula metrics count blocked-looking records from Wordfence's hits/live-traffic data. The plugin currently defines blocked hits using a heuristic equivalent to:

```sql
action LIKE 'blocked:%'
OR status_code IN (403, 503)
```

The public plugin documentation describes:

- `wordpress_wordfence_blocked_events_total` as a cumulative counter of newly observed blocked hits.
- `wordpress_wordfence_blocked_events_window{window="5m|1h|24h|7d"}` as blocked hits in recent windows.

Wordfence's Firewall Summary is a different business-level statistic. It aggregates firewall blocks by Wordfence categories such as Complex and Brute Force. In particular, brute-force totals may include throttling, lockouts, login guessing, password-reset abuse, and related actions that do not necessarily produce one matching `wfHits` row with a `blocked:*` action or a `403/503` response.

Therefore:

- The current Simula metric can be technically correct according to its implementation.
- Its name is ambiguous because it can be mistaken for Wordfence's canonical “Attacks Blocked” total.
- It must not be used as a direct replacement for the Wordfence Firewall Summary.
- The current cumulative counter must not be compared directly with daily, weekly, or monthly Wordfence summary values.

### 1.3 Secondary risks to verify

The implementation must also verify the following possible secondary causes of undercounting or inconsistent windows:

1. Timestamp-column selection in `wfHits`, especially when a preferred column exists but contains null, zero, sparse, or semantically different values.
2. WordPress, database, PHP, and Wordfence timezone/day-boundary handling.
3. Wordfence table retention and cleanup behavior.
4. WordPress multisite and custom table prefixes.
5. Wordfence schema differences between versions and license tiers.
6. WP-Cron/export freshness. This affects how quickly a value appears, although it cannot explain the observed magnitude of the discrepancy by itself.

## 2. Change objective

Implement a new metric family that reproduces the Wordfence Firewall Summary as closely as the available Wordfence database schema permits, while preserving existing metrics and their semantics for backward compatibility.

The change shall provide operators with:

1. A Wordfence-summary-compatible firewall block metric.
2. The existing low-level `wfHits`-based request metric.
3. Explicit source and availability diagnostics.
4. Documentation and examples that prevent the two measurements from being conflated.
5. Tests that validate metric values against known Wordfence-compatible fixtures.

---

## 3. Scope

### 3.1 In scope

- Add Wordfence Firewall Summary-compatible metrics.
- Preserve existing metric names and behavior in the current release line.
- Add clearer aliases for the existing `wfHits`-based metrics.
- Mark ambiguous legacy names as deprecated in documentation, without immediately removing them.
- Add schema detection for the Wordfence aggregate-block data source.
- Add category mapping for Complex, Brute Force, Blocklist, and Other/Unknown.
- Add 24-hour, 7-day, and 30-day summary windows.
- Add data-source availability and collection-success diagnostics.
- Update settings, WP-CLI status, README/readme, Grafana examples, and Prometheus rule examples.
- Add automated unit, integration, and output-validation tests.

### 3.2 Out of scope

- Reimplementing Wordfence's entire analytics UI.
- Scraping or automating the Wordfence admin dashboard HTML.
- Guaranteeing exact parity when Wordfence changes private database schemas or category logic.
- Removing legacy metrics in this change.
- Adding high-cardinality labels such as raw IP addresses, usernames, URLs, reasons, or user agents to Prometheus metrics.
- Treating the low-level request count and the aggregate summary count as interchangeable.

## 4. Required metric model

### 4.1 Existing metrics to retain

The following metrics shall remain available and preserve their current values and meaning:

```text
wordpress_wordfence_blocked_events_total
wordpress_wordfence_blocked_events_window
wordpress_wordfence_blocked_events_by_status_24h
```

Their help text and documentation shall explicitly state that they are derived from matching Wordfence hit/live-traffic rows and are not equivalent to the Wordfence Firewall Summary.

No existing dashboard, alert, or API consumer shall receive silently changed values under these names.

### 4.2 New canonical low-level aliases

Add clearer aliases for the existing hit-row metrics:

```text
wordpress_wordfence_blocked_hit_rows_total
```

Type: Prometheus counter.

Meaning: Cumulative number of newly observed Wordfence hit rows matching the plugin's blocked-hit predicate since the plugin's persisted counter baseline.

```text
wordpress_wordfence_blocked_hit_rows_window{window="5m|1h|24h|7d"}
```

Type: Prometheus gauge.

Meaning: Number of retained Wordfence hit rows matching the plugin's blocked-hit predicate during the specified rolling window.

The alias values must be identical to the corresponding legacy metric values during the compatibility period.

### 4.3 New Wordfence Firewall Summary-compatible metric

Add:

```text
wordpress_wordfence_firewall_blocks_window{
  category="complex|brute_force|blocklist|other",
  window="24h|7d|30d"
}
```

Type: Prometheus gauge.

Meaning: Sum of Wordfence aggregate firewall block counts for the specified category and reporting window.

All normal global labels, including `site`, shall continue to be applied through the existing rendering pipeline.

Example:

```text
wordpress_wordfence_firewall_blocks_window{site="example.org",category="complex",window="24h"} 52
wordpress_wordfence_firewall_blocks_window{site="example.org",category="brute_force",window="24h"} 451
wordpress_wordfence_firewall_blocks_window{site="example.org",category="blocklist",window="24h"} 0
wordpress_wordfence_firewall_blocks_window{site="example.org",category="other",window="24h"} 0
```

The Wordfence-compatible total must be derived in PromQL rather than emitted as a redundant separate series:

```promql
sum by (site, window) (
  wordpress_wordfence_firewall_blocks_window
)
```

### 4.4 Availability metric

Add:

```text
wordpress_wordfence_firewall_blocks_available 0|1
```

Type: Prometheus gauge.

Meaning:

- `1`: the required Wordfence aggregate table and required columns were detected, and this metric family can be collected.
- `0`: the data source is absent or unsupported.

Do not emit fabricated zero-valued category counts when the underlying data source is unavailable. Emit the availability value and the existing bounded exporter error metric/status instead.

### 4.5 Collection-success metric

Add:

```text
wordpress_wordfence_firewall_blocks_collection_success 0|1
```

Type: Prometheus gauge.

Meaning:

- `1`: the latest collection attempt for the metric family completed successfully.
- `0`: the source was detected, but collection failed.

This separates “unsupported/unavailable” from “available but query failed.”

### 4.6 Source metadata metric

Add a bounded informational metric:

```text
wordpress_wordfence_firewall_blocks_source_info{
  source="wfBlockedIPLog",
  schema="detected-variant"
} 1
```

`schema` must come from a finite, code-defined enumeration. It must not contain arbitrary table names, prefixes, SQL messages, versions, or exception text.

The source label shall not be added to the count metric itself because users could accidentally sum semantically different sources.

### 4.7 Optional data-age metric

If the source exposes a reliable latest-period timestamp/day value, add:

```text
wordpress_wordfence_firewall_blocks_latest_timestamp_seconds
```

Type: Prometheus gauge.

This requirement is optional and shall be implemented only if the timestamp can be derived reliably across supported schemas.

## 5. Category mapping requirements

The initial mapping shall be implemented as a single explicit, unit-tested mapping function.

| Exported category | Known Wordfence block types                                                                                |
| ----------------- | ---------------------------------------------------------------------------------------------------------- |
| `complex`         | `fakegoogle`, `badpost`, `country`, `advanced`, `waf`                                                      |
| `brute_force`     | `throttle`, `brute`                                                                                        |
| `blocklist`       | `blacklist`, `manual`                                                                                      |
| `other`           | Any non-null value not in the known mappings, and optionally null/empty values when retained by the source |

Requirements:

1. Mapping values must be defined in one code location and not duplicated across SQL, PHP, tests, and documentation.
2. Unknown block types must not be discarded silently.
3. Unknown values must be aggregated into the bounded `other` category; raw block-type values must not become Prometheus labels.
4. Tests must verify every known mapping and at least two unknown inputs.
5. The implementation shall document that category mappings reflect observed/supported Wordfence schema behavior and may require maintenance after Wordfence updates.

## 6. Time-window semantics

### 6.1 Required windows

The new summary-compatible metric shall support:

- `24h`
- `7d`
- `30d`

### 6.2 Compatibility with Wordfence reporting periods

The development team shall determine and document whether Wordfence's “Today,” “Week,” and “Month” values are:

- rolling intervals, or
- calendar-aligned periods based on the WordPress/site timezone.

The new metric must reproduce Wordfence's actual behavior rather than assuming that dashboard labels mean rolling intervals.

If the source table stores day buckets such as `unixday`, the implementation shall use the same bucket boundaries and inclusion logic as Wordfence where this can be established from Wordfence code or controlled comparison tests.

### 6.3 Label naming decision

Before release, the team shall select one of the following based on verified behavior:

**Option A — rolling windows:** retain `window="24h|7d|30d"`.

**Option B — calendar/reporting periods:** use a semantically correct label such as:

```text
period="today|week|month"
```

Do not publish `window="24h"` if the value actually means “today since local midnight.”

This decision is an acceptance gate.

### 6.4 Timezone requirements

- Use the timezone semantics used by Wordfence's own aggregation/source data.
- Do not mix PHP server timezone, database session timezone, UTC, and WordPress site timezone without explicit normalization.
- Add tests around midnight, daylight-saving transitions where applicable, and week/month boundaries.

---

## 7. Collection and schema requirements

### 7.1 Data source

Prefer Wordfence's aggregate firewall block table, expected to be a prefixed equivalent of:

```text
wfBlockedIPLog
```

The implementation must use the WordPress database prefix and multisite-aware table resolution mechanisms already used by the plugin. No hard-coded `wp_` prefix is allowed.

### 7.2 Query behavior

The collector shall:

1. Detect the table and required columns.
2. Query grouped aggregate values using `SUM(blockCount)` or the schema-equivalent count field.
3. Group values into the bounded exported categories.
4. Generate all required reporting periods from a consistent source snapshot.
5. Cast values safely to non-negative integers.
6. Return zero only when the source exists, the query succeeds, and there are genuinely no matching counts.
7. Avoid SQL interpolation of untrusted values.
8. Avoid one query per category when a single grouped query can provide the source rows efficiently.

### 7.3 Unsupported schemas

When the required source is unavailable or unsupported:

- Emit `wordpress_wordfence_firewall_blocks_available 0`.
- Do not emit category/window series for the unavailable family.
- Set a bounded error/status type, such as `schema_unsupported`, through the existing error mechanism.
- Expose a useful human-readable diagnostic in the admin UI and WP-CLI status, but not as an unbounded Prometheus label.
- Do not fail unrelated metric families.

### 7.4 Performance

- The new query must use indexed source fields where available.
- The collector must not perform a full scan of an unbounded high-volume hit table to reproduce the summary metric.
- The implementation must remain suitable for the plugin's fast collection interval.
- Query duration should be measured in the test harness with a representative fixture volume.
- A target of less than 250 ms for the new collector query on a representative local fixture is desirable; any material regression must be documented.

---

## 8. Backward compatibility and deprecation

### 8.1 No silent semantic change

The implementation shall not replace the data source or meaning of:

```text
wordpress_wordfence_blocked_events_total
wordpress_wordfence_blocked_events_window
```

in a minor release.

### 8.2 Deprecation documentation

Mark the legacy names as deprecated aliases because “blocked events” is ambiguous. Documentation shall state:

> This metric counts matching Wordfence hit/live-traffic rows. It is not the same as the Wordfence Firewall Summary “Attacks Blocked” statistic. Use `wordpress_wordfence_firewall_blocks_window` for dashboard-compatible aggregate reporting.

### 8.3 Removal policy

- Continue emitting legacy names for at least one major release cycle.
- Announce any planned removal in the changelog and upgrade notice.
- Provide dashboard/alert migration examples.
- Do not remove a legacy metric without a major-version change.

## 10. Prometheus recording and validation rules

Add repository examples for the following recording rules.

### 10.1 Wordfence Firewall Summary total

```yaml
groups:
  - name: simula-wordfence-firewall-summary
    rules:
      - record: site:wordpress_wordfence_firewall_blocks:sum
        expr: |
          sum by (site, window) (
            wordpress_wordfence_firewall_blocks_window
          )
```

Use `period` rather than `window` if the verified semantics are calendar based.

### 10.2 Diagnostic ratio

```yaml
- record: site:wordpress_wordfence_hit_rows_to_firewall_blocks:ratio
  expr: |
    sum by (site, window) (
      wordpress_wordfence_blocked_hit_rows_window
    )
    /
    sum by (site, window) (
      wordpress_wordfence_firewall_blocks_window
    )
```

The documentation must describe this as a **diagnostic ratio between different data models**, not as an exporter accuracy percentage.

### 10.3 Divergence alert

An optional example alert may be provided, but it must not claim exporter failure solely because the ratio is low.

Recommended semantics:

```yaml
- alert: WordfenceTelemetrySourcesDiverge
  expr: |
    site:wordpress_wordfence_hit_rows_to_firewall_blocks:ratio < 0.25
    and
    sum by (site, window) (
      wordpress_wordfence_firewall_blocks_window
    ) > 100
  for: 2h
  labels:
    severity: warning
  annotations:
    summary: Wordfence hit-row and firewall-summary telemetry differ materially
    description: The two Wordfence data sources have diverged. This is diagnostic and does not by itself indicate exporter failure.
```

Do not alert on low-volume denominators or division-by-zero cases.

## 13. Acceptance criteria

The change is accepted only when all of the following are true:

1. Existing blocked-event metrics retain their pre-change values for identical fixtures.
2. New low-level alias metrics exactly match the corresponding legacy metrics.
3. The new Firewall Summary metric uses Wordfence aggregate block counts and does not derive its values from `wfHits`.
4. Category totals reproduce the agreed fixture values: 503, 1,342, and 5,854 for the relevant periods.
5. The reporting-period semantics have been verified and correctly named as either rolling windows or calendar periods.
6. Source-unavailable and query-failed states are distinguishable.
7. Unsupported source schemas do not break unrelated exports.
8. Unknown block types are visible only through the bounded `other` category.
9. All unit, integration, smoke, and Prometheus-output validation tests pass.
10. README, WordPress `readme.txt`, changelog, upgrade notice, Grafana examples, and Prometheus examples are updated.
11. Admin UI and WP-CLI status identify the source and latest collection status.
12. No new high-cardinality or sensitive labels are introduced.
13. A real-site comparison against at least one test WordPress/Wordfence instance is documented.
14. The real-site validation records the Wordfence UI capture time, exporter collection time, timezone, license tier, and resulting metric values.

## 14. Real-site validation procedure

For a controlled validation instance:

1. Record WordPress timezone, PHP timezone, database timezone, Wordfence version, Simula plugin version, and license tier.
2. Trigger WordPress cron or run:

   ```bash
   wp simula-security-telemetry export --metrics-only
   ```

3. Record the exact export timestamp.
4. Capture the Wordfence Firewall Summary immediately afterward.
5. Query the new category metrics for the equivalent periods.
6. Sum categories and compare them with the Wordfence UI.
7. Record any difference by category and period.
8. Repeat across a day boundary and, where feasible, a week/month boundary.
9. Confirm that old hit-row metrics continue to differ in a manner consistent with their separate definition.
10. Attach sanitized query output, `.prom` excerpts, and screenshots to the pull request.

Expected result: the new aggregate metric should match Wordfence closely at the same source snapshot and period boundary. Small differences caused by concurrent traffic or collection timing must be quantified and explained.

## 15. Documentation contract

Documentation must contain a prominent explanation similar to:

> Simula exposes two distinct Wordfence blocking measurements. `blocked_hit_rows_*` counts retained hit/live-traffic records matching a blocked-request predicate. `firewall_blocks_*` reports Wordfence's aggregate Firewall Summary counts by category. The values are not expected to be equal because they have different sources, units, retention behavior, and categorization.

For `blocked_events_total`, documentation must also state:

- It is cumulative from the plugin's persisted baseline.
- It is not a daily, weekly, or monthly count.
- It may reset if plugin state is deleted or reinitialized.
- Prometheus `increase()` may be used for interval deltas, subject to counter reset behavior.

For the new summary metric, documentation must state:

- The source table/schema dependency.
- Supported Wordfence versions or tested variants.
- The category mapping.
- Whether periods are rolling or calendar aligned.
- Behavior when the source is unavailable.

## 17. Security and privacy requirements

- Do not expose raw IPs, usernames, URLs, request reasons, user agents, or arbitrary Wordfence block types as labels.
- Keep all new labels bounded and enumerated.
- Sanitize errors in metrics; retain detailed diagnostics only in the protected admin UI, logs, or WP-CLI output.
- Use prepared statements or safe fixed SQL construction.
- Respect least privilege: the plugin requires only read access to Wordfence tables and write access to its configured output path/state.
- Do not change incident-log privacy behavior as part of this work.

## 20. Definition of done

This change is done when an operator can display a Wordfence Firewall Summary-compatible total from the Simula plugin, break it down by Wordfence category, independently inspect low-level blocked hit rows, determine whether each data source is available and fresh, and understand from metric names and documentation why the two measurements may differ—without breaking existing dashboards or silently redefining an existing metric.
