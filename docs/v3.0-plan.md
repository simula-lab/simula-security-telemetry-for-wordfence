# v3.0 Agile Implementation Plan

## Summary

Version 3.0 expands Simula Security Telemetry for Wordfence from aggregate security posture into controlled WordPress asset, access, and indicator-of-compromise telemetry. The release keeps the node_exporter textfile collector model, but adds first-class metrics for the current WordPress version, installed plugin inventory with versions and state, administrator user inventory, and sudden-change signals that can indicate compromise.

The main implementation constraint is Prometheus label cardinality and sensitive-data exposure. Inventory metrics must be explicitly configurable, bounded where practical, documented as potentially sensitive, and safe to disable per metric family.

## Release Goals

- Export the current WordPress core version as metric metadata.
- Export the full installed plugin inventory, including plugin file, name, version, active state, and update availability.
- Export administrator user inventory with stable, privacy-aware identity labels and two-factor coverage state.
- Export WordPress-native change signals for users, roles, plugin/theme state, dangerous settings, cron persistence, content injection, options drift, and suspicious files under WordPress-owned paths.
- Provide a repeatable test workflow so v3.0 can be validated before shipping.
- Split the growing single-file plugin into maintainable include files before adding the largest v3.0 collectors.
- Preserve the existing aggregate posture metrics for backward compatibility.
- Avoid breaking changes for existing v2.x installations, dashboards, alerts, WP-CLI workflows, cron schedules, options, and output formats.
- Add admin UI controls, WP-CLI status output, README/readme.txt documentation, and example dashboard/alert updates for the new metric families.

## Non-Goals

- Do not add a public HTTP metrics endpoint.
- Do not replace the existing node_exporter textfile collector workflow.
- Do not export raw passwords, password hashes, email verification data, session tokens, or application passwords.
- Do not perform unbounded filesystem or content scans during fast exports.
- Do not require a production WordPress site to validate release candidates.
- Do not introduce Composer/autoloading unless a later packaging review shows a clear need.
- Do not remove existing aggregate metrics such as `admin_users_total` and `plugin_update_available_total`.
- Do not rename existing metric families, option keys, cron hooks, WP-CLI commands, settings fields, or incident output fields in v3.0.

## Backward Compatibility Policy

Version 3.0 should be additive by default. Existing v2.x users should be able to upgrade without changing Prometheus queries, Grafana dashboards, alert rules, node_exporter configuration, WP-CLI automation, cron wiring, or incident log consumers.

Compatibility guarantees:

- Existing metric family names remain available.
- Existing labels on current metric families remain stable.
- Existing option keys and state keys continue to load.
- Existing cron hook names continue to work or are migrated safely.
- Existing WP-CLI command names and arguments continue to work.
- Existing incident log `text` and `jsonl` output formats remain compatible.
- Existing default output paths and metric prefix behavior remain compatible.
- Existing aggregate posture metrics remain enabled unless the user previously disabled them.

Allowed v3.0 changes:

- Add new metric families.
- Add new optional labels only on new metric families.
- Add new settings with conservative defaults.
- Add new WP-CLI status fields.
- Add new dashboard panels and alert examples without removing existing examples.

Compatibility testing:

- Golden `.prom` regression fixtures for representative v2.x exports.
- Upgrade tests from v2.x-shaped options and state into v3.0.
- WP-CLI regression tests for existing export, status, metrics-only, incidents-only, and cursor reset commands.
- Incident log regression tests for existing `text` and `jsonl` output.
- Dashboard and alert compatibility checks for existing example metric names.
- File-split regression check proving the same metric families are emitted before and after the split.

Deprecation policy:

- If a v3.0 feature needs a replacement metric, keep the old metric as an alias for at least one major release.
- Document any deprecated metric in README.md and readme.txt.
- Do not remove deprecated metrics in v3.0.

## Architecture Refactor

The current plugin is a single large PHP file. Version 3.0 should split the implementation into focused include files before adding the largest inventory, IoC, snapshot, and testing features.

Goals:

- Keep the main plugin file as a small bootstrap.
- Preserve existing behavior during the split.
- Make collectors easier to test in isolation.
- Keep WordPress.org packaging simple with explicit `require_once` loading.
- Avoid unrelated rewrites while moving code.

Proposed structure:

```text
simula-security-telemetry-for-wordfence.php
includes/
  class-config.php
  class-util.php
  class-settings.php
  class-output.php
  class-wordfence-schema.php
  class-wordfence-collector.php
  class-wordpress-posture-collector.php
  class-inventory-collector.php
  class-ioc-collector.php
  class-snapshot-store.php
  class-incident-exporter.php
  class-metrics-service.php
  class-admin.php
  class-cli.php
```

Main plugin file responsibilities:

- Define plugin metadata and constants.
- Guard direct access.
- Load include files.
- Register activation, deactivation, uninstall, cron, admin, and WP-CLI hooks.

Migration approach:

- Move existing classes into include files without changing behavior.
- Keep class names stable to minimize compatibility risk.
- Add syntax and smoke checks immediately after the split.
- Add or update tests around bootstrap, activation, export, admin, and WP-CLI paths.
- Implement new v3.0 collectors only after the split is verified.

## Proposed Metrics

### WordPress Version

- `wordpress_wordfence_wordpress_version_info{site="...",version="6.x.y"} 1`
- `wordpress_wordfence_wordpress_core_update_available{site="..."} 0|1`

Implementation notes:

- Use `get_bloginfo('version')` or the global `$wp_version`.
- Keep the existing core update metric semantics, but consider whether to retain the current `core_update_available` name as an alias for compatibility.

### Plugin Inventory

- `wordpress_wordfence_plugin_inventory_info{site="...",plugin_file="akismet/akismet.php",name="Akismet Anti-spam",version="5.x",state="active|inactive|network_active",update_available="0|1"} 1`
- `wordpress_wordfence_plugins_installed_total{site="..."} N`
- `wordpress_wordfence_plugins_active_total{site="..."} N`
- `wordpress_wordfence_plugins_inactive_total{site="..."} N`
- `wordpress_wordfence_plugins_network_active_total{site="..."} N`

Implementation notes:

- Use `get_plugins()` for installed plugin metadata.
- Use `is_plugin_active()` and `is_plugin_active_for_network()` for state.
- Use `get_site_transient('update_plugins')` for update availability.
- Include a setting to disable per-plugin inventory independently from aggregate plugin counts.
- Sanitize label values and cap excessively long plugin names.

### Admin User Inventory

- `wordpress_wordfence_admin_user_info{site="...",user_id_hash="...",login_hash="...",display_name_hash="...",two_factor_enabled="0|1"} 1`
- `wordpress_wordfence_admin_users_total{site="..."} N`
- `wordpress_wordfence_admin_users_without_2fa_total{site="..."} N`

Implementation notes:

- Keep raw user IDs, usernames, display names, and email addresses out of Prometheus labels by default.
- Generate stable hashes with `wp_salt()` so operators can correlate changes on the same site without exposing identities.
- Add an explicit advanced setting for identity label mode:
  - `hashed` by default.
  - `id_only` for low-sensitivity internal environments.
  - `disabled` to export counts only.
- Reuse the existing Wordfence 2FA secret table lookup for `two_factor_enabled`.

### User And Role Drift

- `wordpress_wordfence_users_total{site="...",role="administrator|editor|author|subscriber|other"} N`
- `wordpress_wordfence_users_created_window{site="...",role="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_admin_users_created_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_admin_users_modified_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_roles_total{site="..."} N`
- `wordpress_wordfence_role_capabilities_total{site="...",role="administrator|editor|author|subscriber|other"} N`
- `wordpress_wordfence_unexpected_admin_capabilities_total{site="..."} N`

Implementation notes:

- Use `WP_User_Query`, `wp_roles()`, and stored slow-snapshot state.
- Keep role labels bounded to known roles plus `other`.
- Compare current role/capability snapshots against the previous slow snapshot.

### Authentication And Account Events

- `wordpress_wordfence_successful_logins_window{site="...",role="...",window="5m|1h|24h"} N`
- `wordpress_wordfence_password_resets_window{site="...",role="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_user_email_changes_window{site="...",role="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_application_passwords_total{site="..."} N`
- `wordpress_wordfence_admin_application_passwords_total{site="..."} N`
- `wordpress_wordfence_sessions_total{site="...",role="administrator|editor|author|subscriber|other"} N`

Implementation notes:

- Maintain event counters through WordPress hooks such as login, password reset, profile update, and application password changes.
- Persist event timestamps in plugin state or a small plugin-owned option so windowed metrics survive process restarts.
- Avoid exporting usernames, emails, session tokens, or application password names.

### Plugin And Theme Drift

- `wordpress_wordfence_plugins_added_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_plugins_removed_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_plugins_activated_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_plugins_deactivated_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_mu_plugins_total{site="..."} N`
- `wordpress_wordfence_dropins_total{site="..."} N`
- `wordpress_wordfence_active_theme_info{site="...",theme="...",version="..."} 1`
- `wordpress_wordfence_themes_installed_total{site="..."} N`
- `wordpress_wordfence_themes_update_available_total{site="..."} N`

Implementation notes:

- Compare plugin/theme snapshots during slow collection.
- Use `get_mu_plugins()` and `get_dropins()` where available.
- Use `wp_get_themes()` and `wp_get_theme()` for theme inventory.
- Keep detailed per-theme inventory out of v3.0 unless it is needed after plugin inventory is stable.

### Dangerous WordPress Settings

- `wordpress_wordfence_users_can_register_enabled{site="..."} 0|1`
- `wordpress_wordfence_default_role_info{site="...",role="subscriber|administrator|editor|author|contributor|other"} 1`
- `wordpress_wordfence_file_edit_allowed{site="..."} 0|1`
- `wordpress_wordfence_file_mods_allowed{site="..."} 0|1`
- `wordpress_wordfence_debug_enabled{site="..."} 0|1`
- `wordpress_wordfence_debug_display_enabled{site="..."} 0|1`
- `wordpress_wordfence_xmlrpc_enabled{site="..."} 0|1`
- `wordpress_wordfence_rest_api_enabled{site="..."} 0|1`
- `wordpress_wordfence_search_engine_visibility_enabled{site="..."} 0|1`
- `wordpress_wordfence_home_url_info{site="...",hash="..."} 1`
- `wordpress_wordfence_site_url_info{site="...",hash="..."} 1`

Implementation notes:

- Prefer boolean gauges and bounded labels.
- Hash URLs by default to avoid leaking internal hostnames or staging URLs.
- Add alerts for user registration enabled, default role becoming privileged, file editing allowed, debug display enabled, and site/home URL changes.

### Option Table Drift

- `wordpress_wordfence_options_total{site="..."} N`
- `wordpress_wordfence_autoload_options_total{site="..."} N`
- `wordpress_wordfence_autoload_options_bytes{site="..."} N`
- `wordpress_wordfence_options_changed_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_new_autoload_options_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_sensitive_options_changed_window{site="...",option_group="site_url|users|mail|auth|cron|plugins|other",window="1h|24h|7d"} N`

Implementation notes:

- Do not export arbitrary option names as Prometheus labels.
- Use bounded option groups and optionally hash option names in an opt-in diagnostic mode.
- Limit expensive option diffing to slow collection.

### Cron Persistence

- `wordpress_wordfence_cron_events_total{site="..."} N`
- `wordpress_wordfence_cron_hooks_total{site="..."} N`
- `wordpress_wordfence_cron_new_hooks_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_cron_scheduled_events_total{site="...",recurrence="single|hourly|twicedaily|daily|custom"} N`
- `wordpress_wordfence_cron_suspicious_hooks_total{site="..."} N`

Implementation notes:

- Inspect the `cron` option through `_get_cron_array()` where available.
- Compare hook snapshots across slow runs.
- Keep hook names out of labels by default; use suspicious counts and optional hashed hook diagnostics.

### Content Injection Signals

- `wordpress_wordfence_posts_modified_window{site="...",post_type="post|page|attachment|other",window="1h|24h|7d"} N`
- `wordpress_wordfence_pages_modified_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_posts_with_script_tags_total{site="...",post_type="post|page|other"} N`
- `wordpress_wordfence_posts_with_iframe_tags_total{site="...",post_type="post|page|other"} N`
- `wordpress_wordfence_posts_with_suspicious_redirects_total{site="...",post_type="post|page|other"} N`
- `wordpress_wordfence_recent_admin_post_edits_window{site="...",window="1h|24h|7d"} N`

Implementation notes:

- Run content scans only in slow collection.
- Bound post types to common values plus `other`.
- Use simple, transparent indicators first: `<script`, `<iframe`, suspicious redirects, and recently modified pages.

### Uploads And WordPress File IoCs

- `wordpress_wordfence_upload_php_files_total{site="..."} N`
- `wordpress_wordfence_upload_executable_files_total{site="..."} N`
- `wordpress_wordfence_recent_upload_php_files_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_plugin_files_modified_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_theme_files_modified_window{site="...",window="1h|24h|7d"} N`
- `wordpress_wordfence_wp_content_recently_modified_files_total{site="...",area="plugins|themes|uploads|mu_plugins"} N`

Implementation notes:

- Keep filesystem scans bounded by path, file count, and runtime budget.
- Focus on WordPress-owned directories: plugins, themes, uploads, mu-plugins, and known drop-ins.
- Treat uploads containing PHP or executable files as high-signal IoCs.

## Testability Goals

Version 3.0 should add a repeatable test workflow that can validate the plugin before release without relying on a production site.

Required test capabilities:

- Local disposable WordPress test environment.
- Automated PHP syntax and static checks.
- Unit tests for pure helper behavior, label escaping, config defaults, hash generation, and metric rendering.
- Functional tests for plugin settings, collectors, WP-CLI commands, and file output behavior using controlled fixtures.
- Regression tests for previously fixed bugs and documented edge cases.
- Integration tests against a real WordPress installation from the official publisher source with the real Wordfence plugin installed from the official WordPress plugin repository.
- Automated metric-rendering tests for collector output.
- Fixture-based tests for Wordfence-like tables and WordPress state.
- WP-CLI smoke tests for export, metrics-only export, incidents-only export, status, and cursor reset.
- Release-candidate packaging test that installs the generated zip into a clean WordPress site.

Recommended tooling:

- A `docker-compose.yml` or documented local stack for WordPress, MariaDB, and WP-CLI.
- A test bootstrap script under `tests/` or `bin/` that installs WordPress, activates the plugin, and seeds fixtures.
- A separate publisher-integration test profile that downloads official WordPress and installs Wordfence with `wp plugin install wordfence --activate`.
- Version controls for publisher-integration tests:
  - Pinned WordPress and Wordfence versions for release-candidate regression.
  - Latest stable WordPress and Wordfence versions for scheduled compatibility checks.
- Fixture builders for:
  - Wordfence hits and scan issues.
  - Active, inactive, network-active, update-available, MU-plugin, and drop-in states.
  - Administrator users with and without Wordfence 2FA.
  - Suspicious cron hooks.
  - Dangerous WordPress settings.
  - Content injection examples.
  - Uploads containing PHP/executable files.
- Golden `.prom` output checks for representative scenarios.

Pre-shipping test commands should cover:

- PHP syntax checks for all plugin PHP files.
- README/readme.txt consistency checks for metric names.
- Prometheus alert YAML validation.
- Grafana dashboard JSON validation.
- WordPress activation/deactivation smoke test.
- WP-CLI export smoke test.
- Real WordPress plus real Wordfence integration smoke test.
- Generated zip install smoke test.

Test tiers:

- Tier 1, fast local checks: PHP syntax, unit tests, renderer tests, static docs/assets validation.
- Tier 2, functional fixture tests: disposable WordPress with seeded WordPress and Wordfence-like state.
- Tier 3, publisher integration tests: disposable WordPress installed from the official WordPress source and Wordfence installed from the official WordPress plugin repository.
- Tier 4, release-candidate tests: generated zip installed into a clean publisher-based WordPress and Wordfence environment.

Publisher integration environment:

- Run in an isolated Docker network with no public inbound ports.
- Use disposable database volumes and remove them after each run.
- Mount only the plugin under test and a writable test output directory.
- Disable outbound mail and use local-only URLs.
- Write metrics and incident logs to temporary paths under the test workspace.
- Seed only synthetic users, content, uploads, and events.
- Keep credentials generated per run and never commit them.
- Allow outbound network only for fetching official WordPress, Wordfence, and required test dependencies.

SSL/TLS handling in Docker tests:

- Use plain HTTP by default for fast local checks, fixture-based functional tests, WP-CLI tests, and metric rendering tests.
- Add a dedicated HTTPS integration profile for release-candidate and publisher-integration runs.
- Put WordPress behind Caddy, nginx, or Traefik in the HTTPS profile.
- Generate an ephemeral local CA and certificate during test bootstrap.
- Use a stable local hostname such as `wordpress.test`.
- Include subject alternative names for `wordpress.test`, `localhost`, and `127.0.0.1`.
- Trust the generated local CA inside the WordPress, PHP, and WP-CLI containers.
- Set `WP_HOME` and `WP_SITEURL` to the HTTPS URL in the HTTPS profile.
- Keep outbound TLS verification enabled for WordPress, Wordfence, and dependency downloads.
- Do not globally disable SSL verification in WordPress, PHP, cURL, or WP-CLI.
- Require the HTTPS profile for release-candidate validation, but do not require it for every fast local test run.

Publisher integration scenarios:

- Install official WordPress, install official Wordfence, install this plugin zip, and activate all required plugins.
- Run `wp simula-security-telemetry export --metrics-only --scope=slow` and assert Wordfence posture metrics are present.
- Run full export and assert the `.prom` file is produced atomically and remains parseable.
- Verify Wordfence version detection uses the installed real Wordfence plugin.
- Verify WordPress version detection uses the installed real WordPress runtime.
- Verify plugin inventory sees Wordfence and this plugin with correct active state.
- Verify admin inventory sees synthetic administrator users and does not expose raw identities in default mode.
- Deactivate Wordfence and assert failure/posture metrics are controlled and documented.
- Upgrade Wordfence within the same environment when an update is available, then verify inventory and version metrics change as expected.

## Risks And Mitigations

- Label cardinality from plugin and admin inventories.
  - Mitigation: keep detailed inventory opt-in, use bounded labels, and document Prometheus cost.
- Sensitive admin identity exposure.
  - Mitigation: hash identity labels by default and avoid email labels entirely.
- Multisite plugin state complexity.
  - Mitigation: explicitly model `network_active` separately from site-active and test both paths.
- WordPress update transients may be stale or missing.
  - Mitigation: treat missing transients as no update data available and do not fail export.
- Dashboard compatibility.
  - Mitigation: add new panels without renaming existing metric families.
- Expensive content, option, and filesystem scans.
  - Mitigation: run only in slow collection with explicit count and runtime budgets.
- Event metrics are only available after the plugin starts observing events.
  - Mitigation: document them as forward-looking metrics and pair them with snapshot drift metrics.

## Definition Of Done

- New metric families are implemented, configurable, documented, and represented in examples.
- Sensitive inventory metrics require explicit opt-in.
- Backward-compatible aggregate metrics remain available.
- Existing v2.x metrics, settings, WP-CLI commands, cron behavior, and incident output remain compatible.
- The disposable WordPress test harness validates activation, export, WP-CLI operation, and release zip installation.
- PHP syntax checks and example asset validations pass.
- The release zip installs and exports successfully in a test WordPress environment.
